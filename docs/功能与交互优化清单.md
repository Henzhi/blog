# 博客功能与交互优化清单

> 日期：2026-10-07
> 站点：https://henzhi.github.io/blog/（Astro 5 + Fuwari，`base: /blog`）
> 范围：**只审功能与交互设计**，不涉及视觉风格与内容质量。视觉层已由 `docs/UI重构方案.md` 覆盖（设计令牌、栅格、字体、去卡片化均已落地），本文不重复。
> 方法：逐文件读源码 + 无头 Chrome（CDP）在构建产物上实测。所有数字都是实测值，口径随文标注。

## 优先级口径

| 级别 | 定义 | 判断依据 |
|---|---|---|
| **P0** | 明确的失效或可靠性风险，且改动小 | 用户可见的坏链接、对外部网络的运行时依赖、无障碍硬伤 |
| **P1** | 体验显著受益，改动中等 | 交互路径缺失、性能可测量地浪费、对比度不达标 |
| **P2** | 锦上添花，或随内容量增长才显现 | 现在 6 篇文看不出问题，30 篇就是痛点 |

## 一、页面结构

### 1.1 【P0】RSS 自动发现链接缺 `base`，实际指向 404

**现状**：`src/layouts/Layout.astro` 里写的是

```astro
<link rel="alternate" type="application/rss+xml" title={profileConfig.name} href={`${Astro.site}rss.xml`} />
```

`Astro.site` 只是 origin（`https://henzhi.github.io`），不带 `base`。构建产物实测：

```
$ grep 'application/rss+xml' dist/index.html
<link rel="alternate" type="application/rss+xml" title="Henzhi" href="https://henzhi.github.io/rss.xml">
```

真实地址是 `https://henzhi.github.io/blog/rss.xml`。**页脚里的 RSS 链接是对的**（走 `url('rss.xml')`），错的只有 head 里这条自动发现声明。

**建议**：改用已有的 `url()` 工具拼接，与页脚保持一致 ——

```astro
href={new URL(url("rss.xml"), Astro.site).href}
```

**收益**：Feedly / Inoreader / 浏览器 RSS 扩展的「粘贴首页自动发现 feed」现在会拿到 404，修完才能订阅。这是全站唯一的订阅入口链路（页脚那行小字是给已经进站的人看的）。
**验证**：`npm run build` 后 `grep 'application/rss+xml' dist/index.html`，URL 必须含 `/blog/`。

---

### 1.2 【P0】没有 404 页面

**现状**：`src/pages/` 下只有 `[...page].astro` / `about` / `archive` / `categories` / `posts/` / `robots.txt.ts` / `rss.xml.ts`，构建产物 `dist/` 里没有 `404.html`。GitHub Pages 在找不到页面时返回它自己的默认 404 —— 白底、英文、无导航、无回站入口。

**建议**：新增 `src/pages/404.astro`，沿用 `MainGridLayout`，内容给三样东西：一句说明、指向首页/归档/分类的链接、搜索入口。`astro build` 会自动产出 `dist/404.html`，Pages 会识别。

**收益**：旧链接、手打错的 URL、从别处失效跳转进来的访客，现在只能关页面；修完有一条回主站的路。也避免「这站挂了？」的第一印象。
**成本**：一个文件，约 30 行。

---

### 1.3 【P2】没有标签索引页（`/tags/`）

**现状**：标签只在两处出现 —— 侧栏「标签」小组件**只列热度前 8 个**（`Tags.astro` 里 `.slice(0, 8)`），以及文章元信息行里的标签链接（指向 `/archive/?tag=x`）。超过 8 个的标签没有任何一处聚合入口，且侧栏「全部标签 →」指向的是 `/archive/`，那里并不显示标签墙。

**建议**：加 `src/pages/tags.astro`，按文章数倒序列出全部标签（带计数），标签链接复用 `getTagUrl()`；侧栏「全部标签 →」改指向它。

**收益**：标签从「装饰性元信息」变成可用的横向导航。文章多了之后，标签是仅次于分类的第二种组织方式，现在它是残的。
**成本**：一个页面 + 改一个链接。

---

### 1.4 【P2】没有系列 / 专栏结构

**现状**：`src/content/posts/lexagent/01-architecture-overview.md` 已经是系列的第 1 篇（目录分层 + `01-` 前缀），但站内没有任何「本系列其它文章」的入口，读者读完只能靠文章末尾的「上一篇/下一篇」（按时间倒序，不按系列）。

**建议**：frontmatter 加一个可选 `series: string` 与 `seriesOrder: number`；文章页在「上一篇/下一篇」之前插入一个系列导航块（同 series 的文章按 order 列出，当前篇高亮）。不加字段的文章零影响。

**收益**：教程类内容的完读率与二次访问主要靠系列导航撑着；现在一篇长教程读完就是终点。
**成本**：schema + 1 个组件；只对标注了 series 的文章生效。

## 二、导航与检索

### 2.1 【P1】搜索没有键盘路径

**现状**（实测 + 读码）：

| 能力 | 现状 |
|---|---|
| `Cmd/Ctrl + K` 唤起搜索 | 无绑定 |
| `Esc` 关闭面板 | 无（`Esc` 只在 TOC 抽屉里用） |
| 结果列表 `↑/↓` 选择、`Enter` 打开 | 无 |
| `role="listbox"` / `role="dialog"` | 无（面板是个裸 `div`） |
| 搜索按钮 `aria-expanded` / `aria-controls` | 均缺失（实测 `null`） |
| 输入框 `aria-label` | 缺失（只有英文 placeholder） |
| 移动端打开面板后自动聚焦输入框 | 无（还要再点一下输入框） |

`Search.svelte` 的输入框连 `id` 都没有，`aria-controls` 无从挂起。

**建议**：三条最小改动 —— (a) 全局监听 `Cmd/Ctrl+K` 打开面板并 `focus()` 输入框，`Esc` 关闭并把焦点还给触发按钮；(b) 结果项用 `role="option"` + `aria-selected`，↑↓ 移动、Enter 跟随当前项的 `href`；(c) 面板加 `role="dialog" aria-modal` / 或改成 combobox 模式，按钮补 `aria-expanded`/`aria-controls`。

**收益**：键盘与重度用户从「鼠标点两次再打字」变成一次快捷键；也是无障碍审计必查项。
**验证**：CDP 里 `Input.dispatchKeyEvent` 发 `Ctrl+K`，断言 `document.activeElement` 是搜索输入框。

---

### 2.2 【P1】搜索没有空状态和加载状态

**现状**：`Search.svelte` 模板是纯 `{#each result as item}`，**没有 `{:else}` 分支**；组件里声明了 `isSearching` 变量，但模板中**从未使用** —— 也就是说「正在搜」和「没搜到」两种情况，界面上都是同一个空白面板。实测搜一个不存在的词，面板里结果块清空、无任何文字提示。

**建议**：(a) `result.length === 0 && keyword` 时渲染一行「没有匹配的内容」+ 「去归档页翻」链接；(b) 用起 `isSearching` 做一个轻量 loading 指示；(c) 面板里顺带展示 `pagefind` 的 `sub_results`（命中的小节标题），点进去直接到锚点 —— 对长教程文，现在搜到的是整篇，还要自己滚。

**收益**：消除「搜了没反应 = 坏了」的误判；`sub_results` 让长文的检索命中从「篇级」细到「节级」。
**成本**：一个组件内部，约 40 行。

---

### 2.3 【P1】归档页缺筛选输入框与年份分组

**现状**：`archive.astro` + `ArchivePanel.svelte` 只支持「从别的页面带 query 进来」的筛选（`?tag=` / `?category=` / `?uncategorized=`）。归档页自身**没有搜索框、没有年份分组**，只有一条平铺列表。想从「部署」标签换到「架构」标签，必须先回侧栏点。

（实测确认：从标签 A 切到标签 B 时，URL、筛选提示、列表条数都会正确更新，swup 换页后组件重建没问题。问题只在「切换的手段」上。）

**建议**：(a) 顶部加一个只作用于当前列表的即时筛选输入框（纯前端匹配标题/标签，不依赖 Pagefind）；(b) 文章数超过一屏后按年分组，每组一个粘性年份标题 + 计数。

**收益**：6 篇文章时无所谓，30 篇之后归档页是仅次于首页的落点，没有筛选就只能靠 `Ctrl+F`。
**成本**：`ArchivePanel.svelte` 内部改，中等。

---

### 2.4 【P2】导航语义与语言细节

**现状**：

- `<div id="navbar">` 不是 `<nav>`，导航项也在 `div` 里 —— 屏幕阅读器拿不到地标（实测 `document.querySelector('#navbar nav')` 为 `null`）。
- `aria-label` 大量用英文：`"View all posts with the xxx tag"`、`"Back to Top"`、`"Search Panel"`、`"Previous Page"` —— 站点语言是 `zh-CN`，读屏会中英混读。
- 分页禁用态是 `<a href="">`（空 href 会被解析成当前页），而不是 `aria-disabled` + 去掉 href。
- 侧栏「最近更新」的 `WidgetLayout` 传了 `name="最近更新"` 硬编码中文，而分类/标签走 i18n —— 不一致（次要）。

**建议**：导航容器换 `<nav aria-label="主导航">`；把可访问名称统一到 i18n（`zh_CN.ts` 里加 key）；分页禁用态改 `aria-disabled="true"` 并去掉 `href`。

**收益**：读屏与键盘用户的可用性；改动零视觉影响。

## 三、阅读体验

### 3.1 【P1】相关文章缺失

**现状**：文章页只有「上一篇 / 下一篇」（按 `published` 倒序，即时间相邻，不是主题相关）+ 侧栏「最近更新」。`getSortedPosts()` 里 `prev/next` 的赋值逻辑完全基于时间顺序。

**建议**：按「标签重合度」算一个轻量相关度（交集数量 / 并集数量），取前 3 篇，渲染在文末（在版权块之后、上下篇之前）。

**收益**：现在 6 篇文章、标签高度重合（`Astro`/`RAG`/`架构`…），一篇读完跳到同主题另一篇的路径是断的。这是内容量小时**性价比最高**的一个改动。
**成本**：`content-utils.ts` 加一个函数 + 文章页一个区块。

---

### 3.2 【P2】没有阅读进度指示

**现状**：长文（如 `lexagent/01-architecture-overview`）只有左侧 TOC 的高亮项指示当前章节，没有全局进度感。顶部也没有进度条。

**建议**：在正文列顶部加一条 2px 的滚动进度（`scrollY / (docHeight - viewportHeight)`），或在 TOC 顶部放一个「已读 x%」。注意别做成吸顶大色块，与现有克制风格冲突。

**收益**：长文场景下给读者一个「还剩多少」的心理锚点。属可选优化。

---

### 3.3 【P1】`DisplaySettings` 是白加载的

**现状**：`config.ts` 里 `themeColor.fixed = true`，因此 `Navbar.astro` 里那个打开显示设置面板的按钮被条件隐藏了 ——

```astro
{!siteConfig.themeColor.fixed && (<button id="display-settings-switch" ...>)}
```

但 `<DisplaySettings client:only="svelte">` **仍然无条件挂载在 DOM 里**。实测它在首屏加载了 `DisplaySettings.DDrYnRlK.js`（2.1 KB），**并额外向 `api.iconify.design` 拉了一次图标集**（`fa6-solid.json?icons=arrow-rotate-left`，正是"重置主题色"按钮的图标）—— 一个用户永远看不到、也打不开的面板，在首屏发了一次跨域请求。

顺带一个结论：站点锁定了主题色，那么**用户没有任何阅读设置入口**（字号、行宽都不可调）。

**建议**：(a) 短期：`fixed` 时干脆不渲染 `<DisplaySettings>`（省一个 chunk + 一个跨域请求）；(b) 中期：把面板改造成「阅读设置」—— 正文字号三档（16/17/18px）、行宽两档（42rem / 48rem），存 localStorage。这类设置对中文长文是真实需求，比主题色有用。

**收益**：(a) 是纯粹的浪费消除；(b) 让用户能按自己的屏幕和视力调，中文 18px 对某些人是偏小的。

---

### 3.4 【P2】窄屏下的表格与宽代码块

**现状**：KaTeX 公式有 `katex-display-container` 包裹 + OverlayScrollbars 处理（`Layout.astro` 里有专门的 IntersectionObserver），**但表格没有同类处理**，`markdown.css` 里的 `table` 只有边框样式。宽表格在手机上会撑破正文列（`#swup-container` 的 `overflow-hidden` 会直接裁掉右侧，而不是给滚动条）。

**建议**：给 `.custom-md table` 套一层 `overflow-x: auto` 的容器（或在 `markdown.css` 里用 `display:block; overflow-x:auto`），并给 `table` 设 `min-width: max-content`。

**收益**：技术文里的对照表在手机上是高频元素，现在要么被裁要么挤成一团。

---

### 3.5 【P2】标题锚点不能一键复制

**现状**：`rehype-autolink-headings` 生成了 `<a class="anchor" href="#slug">#</a>`，点击只是跳转、更新 URL。想引用某一节给别人的话，得手动从地址栏复制。

**建议**：点击锚点时 `navigator.clipboard.writeText(location.href)` 并给一个短暂的「已复制」反馈（保持 `href` 以免破坏右键复制链接）。

**收益**：教程文被引用/转发到群里的路径更顺。

## 四、互动机制

> 这一节多为**决策项**，不是缺陷。个人记录型博客是否要评论、要统计，取决于你想要多少反馈回路。

### 4.1 【P1/决策】没有评论

**现状**：全站无任何评论组件（`config.ts` 里没有评论配置，`src/components/` 下也没有 Comment 相关文件）。读者读完只有「离开」一条路。

**建议**：三选一 —— **giscus**（GitHub Discussions 承载，零后端、零成本、需要仓库开 Discussions，读者要 GitHub 账号）；**Twikoo / Waline**（自建或 Vercel 部署，支持匿名+邮箱，需要多一个服务）；**不装**（个人记录型博客完全合理）。

**权衡**：如果目标是「记录给自己看」，不装是对的，不必为了"博客应该有"而装。如果要装，giscus 的运维成本最低，但你的读者群体（同学/同行）大概率有 GitHub 账号。

---

### 4.2 【P1/决策】没有任何访问统计

**现状**：无 Umami / Plausible / Google Analytics，也没有任何自定义埋点。**结论**：你无法知道哪篇文章被读过、被读多久、从哪来。Pagefind 是纯前端搜索，**搜索词也不会被记录到任何地方** —— 「读者想找什么但没找到」这个最有价值的信号完全丢失。

**建议**：接一个隐私友好的统计。Umami Cloud 免费档或自建（你有腾讯云 Lighthouse 实例，2C2G 装一个 Umami + PostgreSQL 绰绰有余），约 2KB 脚本，不阻塞渲染。

**收益**：从「凭感觉写」变成「知道哪类文章有人看」。对现在 6 篇的体量，这也是判断「学习笔记 vs 生活记录」哪个方向值得继续投入的唯一依据。

---

### 4.3 【P1】订阅入口太弱

**现状**：全站唯一的 RSS 入口是**页脚一行 13px 的小字**（`Footer.astro`），而且 head 里那条自动发现声明还是坏的（见 1.1）。首页 Hero 的 CTA 只有「按分类浏览」「读文章」，没有订阅。

**建议**：Hero 的按钮组加一个「RSS 订阅」；页脚保留。修完 1.1 之后，这条链路才算完整。

**收益**：让「愿意持续读的人」有一条不用记域名的回路。

---

### 4.4 【P2】无分享 / 无轻量反馈

**现状**：文章页没有分享按钮（复制链接、分享到微信/X），也没有「这篇有用」之类的轻量反馈。

**建议**：分享按钮做一个「复制链接 + 成功态」即可（微信分享靠系统分享面板，网页端做不了太多）。点赞类反馈在无后端时意义有限，除非接 4.2 的统计。

**收益**：低。优先级排在统计和订阅之后。

---

## 五、性能与可访问性

### 5.1 【P0】图标依赖运行时 Iconify API

**现状**（实测，首屏资源列表）：

```
0.0KB  fetch  https://api.iconify.design/material-symbols.json?icons=dark-mode-outline-rounded%2Cradio-button-partial-outlin...
0.0KB  fetch  https://api.iconify.design/fa6-solid.json?icons=arrow-rotate-left
```

`Search.svelte` / `LightDarkSwitch.svelte` / `DisplaySettings.svelte` 用的是 `@iconify/svelte` 的 `<Icon>`，**运行时**从 `api.iconify.design` 拉图标数据。对比之下，`Navbar.astro` 用的 `astro-icon`（`<Icon name="fa6-solid:arrow-up-right-from-square">`）是**构建期内联 SVG**，没有任何网络请求 —— 同一个页面里两套图标机制并存。

**影响**：这三个图标分别属于搜索按钮、主题切换按钮、显示设置按钮。`api.iconify.design` 在国内访问不稳定，一旦请求失败或超时，**按钮变空白方块**（没有本地兜底）。此外还多出一次 DNS + TLS 握手，以及一个第三方域名出现在 CSP 里。

**建议**：把这三个组件的图标换成 `astro-icon/components` 的 `<Icon>`（构建期内联），或改用本地 sprite。搜索框里的那个放大镜、主题切换的三个状态图标、重置按钮图标，都是静态的，没有任何理由走运行时。

**收益**：消除对第三方 CDN 的运行时依赖；少 2 个跨域请求；首屏按钮图标不再有「先空白后填充」的闪烁。也顺带统一了全站图标机制（现在两套并存，是维护隐患）。
**验证**：改完重新构建，实测首屏资源里不应再出现 `api.iconify.design`。

---

### 5.2 【P0】键盘焦点不可见

**现状**（实测）：

```
搜索输入框 computed outline: none 0px / box-shadow: none
```

来源有两处：`src/styles/transition.css:34` 的 `#swup-container { outline: none }`，以及 `Search.svelte` 里的 `input:focus { outline: 0 }` + `outline-0` class。全站**没有任何** `:focus-visible` 自定义样式（`grep -rn "focus-visible" src/` 无结果）。浏览器默认焦点环被砍掉后没有补回任何替代指示。

**建议**：加一条全局规则，只对键盘焦点生效、不影响鼠标点击：

```css
:focus-visible {
  outline: 2px solid var(--primary);
  outline-offset: 2px;
  border-radius: var(--radius-sm);
}
```

并移除 `#swup-container` 与搜索输入框上的 `outline: none`（若视觉上确实不想要默认环，用 `outline: transparent` + 上面的 `:focus-visible` 覆盖，而不是彻底取消）。

**收益**：键盘、开关设备、读屏用户能知道焦点在哪 —— 这是 WCAG 2.4.7（AA）硬性要求，也是 Lighthouse 无障碍项的直接扣分点。

### 5.3 【P1】首屏 JS 有近一半是可以不发的

**现状**（实测，本地无网络延迟，**体积为解码后体积，与线上一致**）：

| 页面 | 请求数 | JS | CSS | 字体 |
|---|---|---|---|---|
| 首页 | 39 | **27 个 / 296 KB** | 5 个 / 170 KB | 2 个 / 86.6 KB |
| 文章页 | 39 | 28 个 / 297 KB | 6 个 / 190 KB | 2 个 / 86.6 KB |

指标：FCP 536ms / LCP 1704ms / CLS 0（1440×900，本地服务）。

按体积看几个大头，都能解释清楚：

| 资源 | 体积 | 问题 |
|---|---|---|
| `photoswipe.esm.js` | 59.0 KB | **首页也加载**，而首页没有任何图库。图片灯箱只在正文出现图片时才有用 |
| `pagefind.js` | 44.5 KB | 首屏就加载（还额外先发一次 `HEAD` 探测文件是否存在） |
| `zh_TW.js` | 7.3 KB | 站点语言是 `zh_CN` |
| `render.js` + `props.js` | 34.1 + 11.9 KB | Svelte 5 运行时，为 3 个很小的组件（Search / LightDarkSwitch / DisplaySettings）服务 |
| 其余 Svelte chunk（`each` / `client.svelte` / `input` / `Icon` 等） | ~30 KB | 同上，chunk 切得太碎，27 个请求里有近 20 个是 1–5 KB 的碎片 |

根因之一是 `src/i18n/translation.ts` **静态 import 了全部 10 种语言包**（`en/es/id/ja/ko/th/tr/vi/zh_CN/zh_TW`），而 `siteConfig.lang` 固定 `zh_CN`。实测首屏确实拉了 `zh_TW.js`。

**建议**（按性价比排序）：

1. **photoswipe 改为按需加载** —— 把 `Layout.astro` 里那段 lightbox 初始化改成「检测到 `.custom-md img` 或 `#post-cover img` 存在时才 `import()`」。首页直接省 59 KB。
2. **语言包改为按需** —— `translation.ts` 改成只保留 `zh_CN`（删掉其余 import），或改成 `import.meta.glob` 动态加载。这是最简单的一刀。
3. **pagefind 延后到首次交互** —— 现在是页面加载即 `fetch HEAD` + `import`。改成「鼠标悬停/聚焦搜索框时再加载」或 `requestIdleCallback`，首屏少 44.5 KB。
4. **合并 Svelte 组件** —— Search / LightDarkSwitch / DisplaySettings 三个组件各自一个 chunk + 各自的 Svelte runtime 分片，考虑合并成一个 `client:only` 岛。

**收益**：三项做完，首屏 JS 从 ~296 KB 降到 150 KB 量级，请求数从 27 降到 15 以内。在移动网络下这是数量级的差别。
**验证**：重跑 CDP 资源统计（方法见文末），对比 JS 总量与请求数。

### 5.4 【P1】次级文字对比度不达标

**现状**：用 oklch → sRGB 换算后按 WCAG 公式实测（背景分别为亮色 `--page-bg: oklch(0.95 0.008 250)`、暗色 `oklch(0.145 0.008 250)`）：

| 类 | 用途 | 亮色 | 暗色 |
|---|---|---|---|
| `.text-90` | 正文/标题 | 15.38:1 ✅ | 15.93:1 ✅ |
| `.text-75` | 次级正文 | 9.60:1 ✅ | 11.08:1 ✅ |
| `.text-50` | 摘要、说明文字 | **3.86:1 ⚠️** | 5.33:1 ✅ |
| `.text-30` | 日期、字数、标签、页脚 | **2.08:1 ❌** | **2.59:1 ❌** |
| `.text-25` | 更弱 | 1.82:1 ❌ | 2.14:1 ❌ |
| `--primary`（链接） | 正文链接 | **4.19:1 ⚠️** | 8.01:1 ✅ |

WCAG AA 正文要求 4.5:1，大字号（≥18.66px 粗体 / ≥24px）要求 3:1。`.text-30` 用在**日期、字数、标签、归档页整列日期、页脚**——全是 13px 正文大小，2.08:1 意味着在亮色模式下基本是「看得到形状、读不清字」。

`UI重构方案.md` 的验收标准里有一条「对比度：深色模式正文 ≥ 7:1」，实测 15.93:1 是通过的 —— 但那条只覆盖了**正文**，元信息层没被纳入验收。

**建议**（`src/styles/main.css` 的 5 个类 + `variables.styl` 的 `--primary`）：

- `.text-30` → 提到 `text-black/45` / `dark:text-white/45`（约 3.7:1 / 5.9:1；若目标是 4.5 则用 `/50`）
- `.text-50` → 提一档到 `/55`~`/60`
- `--primary` 亮色 `oklch(0.55 0.14 250)` → 降到 `oklch(0.50 0.15 250)` 左右（约 4.8:1）

**收益**：全站所有元信息从「勉强能看」变成「正常可读」，这是最高频被扫视的信息层。改动集中在一个文件，零结构风险。
**验证**：改完用 axe DevTools 或 Lighthouse 无障碍跑一遍；也可用本次的换算脚本复算。

### 5.5 【P1】没有全局的动效降级

**现状**：`grep -rn "prefers-reduced-motion" src/` 只有一个结果 —— `TOC.astro` 内部。而全站有：`.onload-animation`（`translateY(2rem)` + opacity 的入场动画，**每页每个区块都有**）、swup 换页的 `translate-y-4` 位移淡入淡出、大量 `transition-colors`。对前庭功能敏感的用户，页面每次切换都在动。

**建议**：在 `transition.css` 加一段全局降级：

```css
@media (prefers-reduced-motion: reduce) {
  .onload-animation { animation: none; opacity: 1; }
  html.is-animating .transition-swup-fade { transform: none; }
  *, *::before, *::after { transition-duration: 0.01ms !important; }
}
```

**收益**：一次性覆盖全站，符合 WCAG 2.3.3。TOC 已经这么做了，说明你认这个原则，只是没铺开。
**注意**：别把 `.onload-animation` 直接删动画——它是靠动画结束才把 opacity 推到 1 的，降级里必须显式补 `opacity: 1`，否则内容会停留在 `opacity: 0`（这个坑在无头截图那条经验里已经踩过）。

### 5.6 【P1】Hero 头像是跨域外链，且有重定向

**现状**：`profileConfig.avatar = "https://github.com/Henzhi.png?size=128"`。这个 URL 会 302 重定向到 `avatars.githubusercontent.com`，而 Hero 头像是**首屏元素**（`loading="eager"`），LCP 会等它。页面里没有 `preconnect`/`dns-prefetch` 到这两个域名。国内访问 GitHub 图片资源的稳定性是已知问题。

**建议**：二选一 —— (a) 下载到 `public/` 用本地图（顺带能用 `astro:assets` 优化，且离线可看）；(b) 保留外链，但 head 里加 `<link rel="preconnect" href="https://avatars.githubusercontent.com" crossorigin>` 并在 `<img>` 上加 `onerror` 兜底占位。

**收益**：(a) 彻底消除首屏的第三方依赖（头像挂掉时 Hero 是"你是谁"的落点，最不该缺）；(b) 至少省掉一次 DNS + TLS + 302。

### 5.7 【P2】CSS 与字体的体积

**现状**：单文件 `_page_.D7kxgkRr.css` **103 KB**（首页共 5 个 CSS 文件 170 KB 解码）；字体 2 个 86.6 KB（Inter latin 47.1 + JetBrains Mono latin 39.5）。另外 `Layout.astro` 顶部无条件 `import "katex/dist/katex.css"`，**没有公式的页面也加载 KaTeX 样式**（文章页 CSS 比首页多约 20 KB，主要来自这里）。

**收益**：首页 CSS 可降 20–30 KB；字体预加载能改善 LCP 稳定性。属渐进优化。

### 5.8 【P2】分享卡片没有图

**现状**：`Layout.astro` 里 `twitter:card` 声明为 `summary_large_image`，但**没有 `og:image`**（`posts/[...slug].astro` 的 jsonLd 里也留着 `// TODO include cover image here`）。分享到群里时卡片没有配图。

### 5.9 【P2】滚动处理未节流

**现状**：`Layout.astro` 里 `window.onscroll = scrollFunction`，函数内做了多次 DOM 查询与 `getBoundingClientRect`（`backToTopBtn` / `toc` / `navbar` 三处 class 切换），**没有 rAF 节流**。对比之下 `TOC.astro` 内部的 `onScroll` 是带 rAF 节流的。

**收益**：滚动流畅度，低端机/长文页更明显。改动 10 行。

### 7.4 过程中发现并顺手修掉的问题

1. **Ctrl+K 会把自己刚打开的面板关掉**（本次引入、验收时发现）：桌面输入框的 `on:focus` 会立刻用当前关键词搜一次，而关键词为空时 `search("")` 会收起面板 —— Ctrl+K 打开后紧接着聚焦输入框，于是刚展开又被收起。已改为「聚焦时若关键词为空则什么都不做」。
2. **灯箱换页后可能失效的隐患**：`content:replace` 里 `destroy()` 之后没有把模块级变量置空，而 `page:view` 又会重建 —— 原来的写法靠「无条件重建」掩盖了这一点，改成按需加载后必须显式置空，否则第二次换页就不会再重建。顺手修正。
3. **Tailwind 透明度刻度**：`text-black/62` 这类值不在刻度（每 5 一档）上，构建直接报错；已全部改到刻度内的值（55 / 60 / 65）。
4. `photoswipe` 的 CSS 最初仍会在首屏加载 4.4 KB（Vite 会把动态 import 的 CSS 挂到父 chunk 的依赖上）。改成 `import "photoswipe/style.css?url"` 只取地址、用到时再插 `<link>`，首屏归零。

### 7.5 遗留

- **图标本地化需要人工维护**：新增图标时要跑一次 `node scripts/gen-local-icons.mjs`（脚本头注释写了用法），忘了跑就会在页面上看到空白图标 —— 这是用构建期换取运行时可靠性的代价。
- **语言包只保留 en + zh_CN**：`src/i18n/languages/*.ts` 一个都没删，恢复多语言只要把 import 加回 `translation.ts` 的 map 即可。
- **`Photoswipe` 的 CSS 注入是运行时插 `<link>`**，理论上第一次打开灯箱会有一帧无样式；实测无感，但如果以后正文图片变多、且在意这一帧，可以改回静态引入。
